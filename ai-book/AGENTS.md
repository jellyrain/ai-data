# ai-book 说明文档编写规范

适用范围：本目录中的文档及文档站点维护。编写前同时遵守项目根目录的 [AGENTS.md](../AGENTS.md) 和[开发规范](../需求文档/development-standards.md)。

`ai-book/docs` 是 API、DAS 和 Web 的使用、部署、接口、开发及更新说明的统一编写位置。站点使用 VitePress + Teek，沿用现有 Markdown、Frontmatter、编号目录和永久链接写法。

## 文档更新触发条件

只有用户明确要求更新文档时，才按获准范围修改本目录，包括说明页、归档记录、首页和站点配置。日常开发、功能新增、接口调整和问题修复均不自动触发文档维护。需要集中整理时，由用户明确发起；以下编写和验证规则在该次获准文档任务中执行。

## 1. 七类文档

保留现有目录编号，新内容按以下分类归入对应目录。新增分类页面时建立相应目录，并同步站点导航。

| 分类     | 目录                | 读者与内容                                                                         |
| -------- | ------------------- | ---------------------------------------------------------------------------------- |
| 指南     | `docs/01.指南/`     | 初次了解项目的人：产品介绍、API/DAS/Web 职责、核心概念、快速上手                   |
| API 参考 | `docs/02.API/`      | 调用方与前端开发者：认证、接口参数、响应、错误码、SSE、调用示例                    |
| 开发指南 | `docs/03.开发/`     | 开发者：工程结构、本地开发、共享合同、模块实现、测试、扩展与文档维护               |
| 部署运维 | `docs/04.部署运维/` | 部署人员：环境、打包、服务配置、启动、DAS 接入、升级、备份恢复与故障排查           |
| 使用手册 | `docs/05.使用手册/` | 业务用户：对话分析、澄清追问、报表、参数、画布、分享与导出                         |
| 管理手册 | `docs/06.管理手册/` | 管理员：用户角色、权限、数据源与目录、模型、Agent、Skill、指标、知识审核与后台任务 |
| 归档记录 | `docs/07.归档记录/` | 使用者与维护者：按版本或日期查阅新增功能、修复、调整和升级事项                     |

API、DAS、Web 按主题需要作为二级分类；跨服务任务放在一篇完整流程中说明。每个主题保留一份主要说明，其他分类通过链接引用。

例如，获取 `api-registration.jwt`、复制 API 公钥、启动 DAS 和检查注册结果归入“部署运维 → DAS 接入”；签发凭据接口的参数和响应归入“API 参考 → DAS 管理”，两篇互相链接。

需求与设计继续维护在项目的 `需求文档/`，实施清单、交付说明和验证经过维护在 `任务交接/`。面向读者的操作说明及更新记录写入本目录。

## 2. 编写依据与已有内容

- 先核对当前代码、配置 Schema、路由、共享合同和验证记录，再编写字段、路径、命令及行为说明。
- 当前 API/DAS 的实现位于 `../ai-data/`。获准更新 Web 操作说明时，以实际页面和交互验收为依据，规划内容明确标注状态。
- 现有页面提供格式参考；其中涉及的产品名称、技术栈、接口前缀、认证方式和响应结构逐项按本项目实现核对。
- 修改 README 时保留原有内容，追加规范入口、分类和必要说明。已有内容需要修订或迁移时先列出具体范围，按项目协作规则取得批准。
- 维护已有永久链接及引用关系；文件移动时核对导航、图片和站内链接。
- 示例使用虚构标识、测试数据或清晰的占位值。认证信息通过占位符或交互输入表达。

## 3. 文件、Frontmatter 与链接

章节目录和页面沿用 `两位序号.中文名称`，例如 `04.部署运维/01.首次部署/03.DAS接入.md`。序号控制同级顺序，正文标题表达实际主题。归档可以按年份分组，文件名包含记录日期与更新主题。

站点正文页使用以下 Frontmatter，按实际内容填写：

```yaml
---
title: DAS 接入
date: 2026-09-22 09:00:00
permalink: /deployment/das-registration
categories:
  - 部署运维
tags:
  - DAS
  - 注册
---
```

- `title` 使用清晰的中文主题。
- `date` 填写实际创建时间，采用东八区 `YYYY-MM-DD HH:mm:ss`；普通内容修订保留创建时间。
- `permalink` 使用稳定、唯一的英文小写路径，词之间用连字符。常用前缀为 `/guide/`、`/api/`、`/develop/`、`/deployment/`、`/manual/`、`/admin/`、`/changelog/`。它表示文档地址，请求路径在正文单独声明。
- `categories` 对应七类之一；`tags` 补充模块或主题。
- `top`、`sticky` 等展示字段按实际首页或置顶需要使用。
- 沿用站点标题渲染，正文从 `##` 开始，小节使用 `###`。站点外的 README、编写规范和交接文件使用普通 Markdown 标题。
- 站内文章优先链接到 `permalink`，图片放入 `docs/public` 对应主题目录，并以 `/主题/文件名` 引用。
- 正文与表格中的对象结构使用行内代码，例如 `{ items: [...] }`，避免花括号被 Markdown 属性插件解释。

分类的 `目录.md` 沿用已有写法：

```yaml
---
title: 部署运维
date: 2026-09-22 09:00:00
permalink: /deployment
layout: page
catalogue: true
path: 04.部署运维
desc: API、DAS 和 Web 的部署与维护
sidebar: false
article: false
---
```

`path` 对应 `docs` 下的实际目录。新增顶层分类时核对 `docs/.vitepress/config.ts` 中的导航项、链接与 `activeMatch`。

## 4. 操作说明写法

先说明完成后能得到什么，再按实际操作顺序编写。部署运维、使用手册和管理手册可采用下列结构，篇幅按任务复杂度调整：

```markdown
## 用途

说明这项操作解决什么问题、完成后得到什么结果。

## 前提

说明所需角色、已启动的服务、已有配置及输入材料。

## 操作步骤

### 1. 第一步

说明在什么机器、目录、终端或页面执行，给出操作及预期结果。

### 2. 第二步

引用上一步得到的值，说明保存位置或下一步如何使用。

## 确认结果

给出健康接口、状态、返回字段或页面表现，帮助读者确认操作成功。

## 常见问题

按已知现象说明原因和处理办法。
```

命令块标注实际语言，例如 `powershell`、`bash`、`json`。跨平台命令存在差异时分别给出，标明执行目录、需要替换的变量和文件路径的解析基准。示例中的命令应能按顺序衔接。

配置字段较多时使用“字段、类型、必填、默认值、说明”表。默认值和可选性以当前 Schema 为准。说明文件下载、复制或生成操作时写清来源、目标路径及确认方法。

## 5. API 参考写法

沿用现有“请求信息 → 参数表 → 响应”的写法，一个页面说明一个接口或一组紧密相关的操作：

1. **请求信息**：方法、路径、用途、认证方式、所需角色或权限。
2. **请求参数**：分别列出路径、查询、请求头及请求体参数；说明类型、必填、默认值、范围和相互约束。
3. **请求示例**：给出合法请求，认证使用 `<ACCESS_TOKEN>` 等占位符。
4. **成功响应**：实际 HTTP 状态码、响应字段表和合法 JSON 示例；空响应说明状态码。
5. **失败响应**：代码中实际存在的状态码、错误码、触发条件及处理建议。
6. **行为约定**：按接口需要说明版本、幂等、分页、异步状态、取消或权限范围。

参数表示例：

| 字段        | 位置 | 类型   | 必填 | 说明                                     |
| ----------- | ---- | ------ | ---- | ---------------------------------------- |
| `serviceId` | 路径 | string | 是   | 已在 API 受信任服务配置中启用的 DAS 标识 |

该示例对应 `POST /admin/data-access/services/:serviceId/credential`。当前成功响应为 `service_id` 和 `credential`；字段名及包装结构按各接口的实际响应书写。

SSE 文档需写明连接与认证、事件名称、事件 ID 或序号、载荷、完成与失败表现及恢复约定。流示例用 `text` 代码块，JSON 示例使用可解析的完整值。

## 6. 开发说明写法

按照“模块职责 → 目录与依赖 → 合同或调用边界 → 关键流程 → 扩展示例 → 验证方式”组织。读者需要能够找到实现入口，理解数据从何处进入、如何处理及输出给谁。

示例遵守当前项目的 TypeScript、Schema、身份与权限规范。引用最小必要代码，较长实现链接到对应源码或接口页。流程较复杂时配流程图；在站点确认相应图表语法可渲染后使用。

## 7. 归档记录写法

归档记录用于查阅项目更新。用户明确要求更新文档后，将本次指定范围内已完成的更新按发布版本或日期整理成篇，明确影响 API、DAS、Web 或文档中的哪些部分。正式版本号以实际发布信息为准，尚未发布版本时使用日期和更新主题。

- 标题采用“日期 · 更新主题”或实际版本号与主题。
- `categories` 使用 `归档记录`，`permalink` 使用稳定的 `/changelog/日期-主题`。
- 文件可放在 `docs/07.归档记录/2026/01.2026-09-22.更新主题.md`；同级使用唯一的两位序号，避免主题将年份识别为重复排序号；归档汇总页按日期由新到旧列出链接。
- 功能说明写清用户能做什么，修复说明写清触发条件和修复后的表现。
- 涉及配置、接口或数据兼容性时，写明受影响范围及升级所需操作，链接到对应详细说明。
- 区分已验证环境、尚待验证的平台和待实现内容；历史记录保留当时适用的版本与日期。

正文模板如下，只保留本次有实际内容的章节：

```markdown
## 更新概览

说明更新日期或实际版本、涉及的组件和主要变化。

## 新增

- 描述新增能力及其使用入口。

## 调整与修复

- 描述行为变化、触发条件和适用范围。

## 升级事项

列出配置、接口、数据库或部署步骤需要采取的操作，并链接到详细说明。

## 验证与适用范围

说明完成验证的版本、平台或场景，以及影响使用的已知限制。

## 相关说明

链接到本次更新涉及的操作指南和接口参考。
```

在获准的文档更新范围内，归档记录、功能说明同步维护：前者记录变化及生效时间，后者反映当前使用方式。

## 8. 提交前检查

1. 检查主题分类、Frontmatter、字段名、命令、权限和示例是否符合当前实现。
2. 检查永久链接唯一性、站内引用、图片路径及导航；保留已有 README 内容。
3. 使用已有格式工具检查本轮 Markdown，预览参数表、代码块、目录和提示容器。
4. 在 `ai-book` 目录执行 `pnpm docs:build` 验证站点；需要预览时执行 `pnpm docs:dev`。依赖安装、升级和卸载由用户操作。
5. 本次获准文档更新涉及的说明与归档记录保持一致，在项目 `任务交接/` 保存交付说明、流程图和实际验证结果。
