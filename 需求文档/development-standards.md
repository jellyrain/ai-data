# AI BI 开发规范

版本：v0.2  
状态：生效  
设计基线日期：2026-09-11  
适用范围：当前工作区全部应用与共享包  
关联文档：[technical-design.md](./technical-design.md) · [contracts.md](./contracts.md) · [development-checklist.md](./development-checklist.md)

## 1. 目标

本规范保证 AI BI 的代码具备一致的结构、可读的业务边界、可验证的合同和可追溯的查询行为。

## 2. 通用原则

- 使用 Node.js、TypeScript、pnpm Workspace。
- 业务数据查询只能表达为受控 DSL，并由 Data Access Service 编译为参数化只读请求。
- API 管理用户、组织、业务关系、指标统计规则和权限，生成最终可执行 DSL；Data Access Service 完成校验、执行、匿名化/脱敏和返回。
- 对外输入、跨服务通信和持久化边界必须先校验，再进入业务逻辑。
- 优先写清楚业务意图和边界，再抽取通用代码。
- 每次变更只覆盖当前需求相关范围，并保留已有有效实现。
- 开始开发任务前，必须先读取并遵守 `no-negative-echo` 和 `stop-that-shit` Skill，如果已经读过，就不需要再读，除非对于skill规范不确定了才再读
- 两个 Skill 的要求发生冲突时，以 `stop-that-shit` 为准。

## 3. Monorepo 目录规范

```text
ai-data/
├─ apps/
│  ├─ web/                 Vue Web 应用
│  ├─ api/                 Fastify API 与 Agent Gateway
│  └─ data-access/         独立只读 Data Access Service
├─ packages/
│  ├─ contracts/           Zod Schema 与共享 TypeScript 类型
│  ├─ metadata/            元数据库接口与 SQL Server 实现
│  ├─ domain/              指标、记忆、审核、报告领域逻辑
│  ├─ skills/              Git 管理的 Skill Markdown
│  └─ config/              非敏感配置和配置读取逻辑
└─ package.json            根脚本与 Workspace 管理
```

规则：

- `apps` 放可独立启动、构建和部署的应用。
- `packages` 放被一个或多个应用复用的代码、合同或资源。
- 业务功能按领域或 feature 分类，避免把所有文件堆放在 `src` 根目录。
- 测试统一放在对应包的 `tests` 目录，不放入 `src`。
- 测试目录镜像 `src` 的业务分类结构。

## 4. TypeScript 文件与命名规范

| 对象           | 规范                                                   | 示例                                       |
| -------------- | ------------------------------------------------------ | ------------------------------------------ |
| 文件名         | 小写 kebab-case。                                      | `data-access-request.ts`                   |
| 分类目录       | 小写 kebab-case，按职责命名。                          | `access/`、`query/`                        |
| 变量与函数     | camelCase，名称体现业务动作或含义。                    | `queryAccessContextSchema`、`compileQuery` |
| 类型、接口、类 | PascalCase。                                           | `QueryAccessContext`、`QueryResult`        |
| 常量           | camelCase；仅真正全局不变的常量使用 UPPER_SNAKE_CASE。 | `maxQueryLimit`、`DEFAULT_TIMEOUT_MS`      |
| API / DSL 字段 | 使用项目已定义的 snake_case 合同字段。                 | `source_id`、`analysis_run_id`             |
| 布尔值         | 使用 `is`、`has`、`can`、`supports` 等可读前缀。       | `isHealthy`、`supportsJoins`               |

## 5. Imports 与 Exports

### 5.1 Imports

- TypeScript 相对导入不写 `.js` 或 `.ts` 扩展名。
- 仅用于类型的导入使用 `import type`，混合导入可写作 `import { value, type Type }`。
- 第三方依赖导入在前，相对导入在后。
- 只导入当前文件实际使用的内容。
- 应用使用共享合同时统一从 `@ai-data/contracts` 导入，不引用其内部 `src` 路径。
- 跨工作区包引用遵守目标包 `package.json` 的 `exports`；例如 `@ai-data/metadata/sqlserver` 是公开子入口。相对路径和绝对路径均不能绕过包入口。
- 应用源码由各自应用维护，应用之间不相互导入源码，共享包也不能反向导入应用；复用能力放入 `packages` 并公开导出。
- `pnpm lint` 自动检查类型导入与工作区依赖边界；工程规则的合法及违规样例纳入 `pnpm test:engineering`。

```ts
import { z } from "zod";

import type { QueryAccessContext } from "@ai-data/contracts";
import { queryAccessContextSchema } from "@ai-data/contracts";
```

### 5.2 Exports

- 一个文件的 export 统一放在文件最后。
- Schema 文件只导出运行时 Schema。
- `*-types.ts` 文件只导出 TypeScript 类型。
- `packages/contracts/src/index.ts` 是 contracts 的唯一公共出口。
- 公共 `index.ts` 负责导入和导出；领域类型定义在所属分类的 `*-types.ts` 文件中。
- 新增公共合同后，必须同步加入 `src/index.ts`。

```ts
export { queryAccessContextSchema };

export type { QueryAccessContext };
```

### 5.3 依赖装配与错误边界

- 应用装配使用具名依赖对象，当前启用模块的依赖在类型中明确为必需项；启动阶段应能定位缺失项。
- 服务声明实际使用的接口能力，测试按相同能力提供替身；单模块测试可直接注册路由。
- 已分类业务失败使用稳定错误码。API 内部使用 `ApplicationError`，运行时错误类由应用维护，共享 contracts 保存错误码与响应结构。
- 在单一 HTTP 边界映射状态、公开说明和请求 ID。程序按错误码分支，提示文案仅用于解释。
- 适配器负责转换已知的驱动、传输和外部认证异常，并通过 `cause` 保留原因。持久化记录和上游响应的合同校验失败属于内部数据错误。
- 未知异常返回通用内部错误说明，原始异常与请求 ID 写入服务端日志；向外发送上游失败时使用适合公开的说明。

## 6. Zod 合同规范

### 6.1 Schema 与类型分离

每个合同分类使用一对文件：

```text
query/
├─ data-access-request.ts        Zod Schema
└─ data-access-request-types.ts  从 Schema 推导的 TypeScript 类型
```

具有运行时 Schema 的数据形态，其 TypeScript 类型必须从对应 Schema 推导，保持运行时校验与编译期类型一致。跨服务合同和数据库读取记录都遵循这条规则；仓储中直接使用 `.parse()` 的推导结果时，可以保留局部推导类型。

```ts
/** API 传给 Data Access Service 的查询审计上下文类型。 */
type QueryAccessContext = z.infer<typeof queryAccessContextSchema>;
```

内部对象经过字段改名、空值处理、JSON 解析等明确转换后，可以在所属业务模块的 `*-types.ts` 中独立定义类型。仓储或转换函数应声明输出类型，负责将已校验的输入转换为业务对象；形态相同的嵌套字段、枚举与约束继续复用对应 Schema 的推导类型或已有公共类型。

例如，数据库记录的 `target_database: string | null` 由读取 Schema 校验，仓储将其转换为运行时配置的 `targetDatabase?: string`。两者分别描述持久化形态和连接器使用的业务形态。

数据库行 Schema 按数据源、密钥、对象暴露、HTTP 映射等职责组织在 `metadata`；转换后的运行时类型归对应业务模块。查询审计事件的 Schema 与推导类型归查询执行模块，审计仓储负责校验和写入。多处使用的持久化 JSON 解析函数集中在 `metadata/parse-persisted-json.ts`。

### 6.2 Schema 编写要求

- 所有服务边界对象使用 `.strict()`。
- 字符串 ID 使用 `.min(1, "字段名 不能为空")`。
- 数据对象、字段、别名等 SQL 标识符使用固定正则白名单。
- 枚举只列出当前已审核的能力或状态。
- 需要默认值时使用 `.default(...)`，并在注释中说明默认行为。
- 互斥字段、依赖字段和操作符组合使用 `.superRefine(...)` 校验。
- 查询结果行数、分页量、超时等资源边界必须有明确上限。
- 日期时间使用东八区 `YYYY-MM-DD HH:mm:ss`，并校验真实日期。

### 6.3 Zod 注释规范

中文注释主要服务熟悉 TypeScript 的开发者，帮助其理解业务含义、约束和设计原因。Zod 中容易误读的机制应补充必要技术说明。注释围绕字段、对象或一组业务规则组织，可以由一段说明覆盖连续的链式调用。

| 位置或机制                                  | 注释要求                                                     |
| ------------------------------------------- | ------------------------------------------------------------ |
| Schema 声明前                               | 说明用途和适用边界，必要时注明数据来源与调用方。             |
| 业务字段                                    | 说明业务含义；来源、单位、作用范围等影响使用时一并说明。     |
| `.string()`、`.number()`、`.array()` 等     | 选择该基础类型有特殊理由时说明理由。                         |
| `.min()`、`.max()`、`.int()`、`.positive()` | 说明限制的业务依据或保护目标，可与字段说明合并。             |
| `.enum()`                                   | 说明枚举代表的能力或状态，以及影响使用的重要差异。           |
| `.optional()`、`.nullable()`、`.default()`  | 说明省略、空值和默认值的业务语义，以及后续校验对它们的限制。 |
| `.strict()`                                 | 在所属 Schema 的边界说明中交代未知字段的处理约定。           |
| `.refine()`、`.superRefine()`               | 在复杂校验前集中说明跨字段规则和校验职责。                   |
| 递归、联合类型、输入转换等                  | 对容易误读的机制说明选择原因及其执行作用。                   |

例如，以下字段说明数据来源和审计用途，基础类型与非空要求由代码表达：

```ts
/** 当前分析运行标识，由 API 分配，用于关联 DAS 查询审计。 */
analysis_run_id: z.string().min(1),
```

字段的可选性受到跨字段规则约束时，应说明实际使用条件与校验位置：

```ts
/**
 * 过滤值的形态由 op 和 data_type 共同决定，在下方 superRefine 中联合校验。
 * is_null、not_null 必须省略此字段；其他操作必须提供值。
 */
value: z.unknown().optional(),
```

对有独立业务含义的嵌套结构，可以提取具名 Schema，并在其声明处集中说明规则。名称、字段和注释应共同帮助读者定位职责。

## 7. 注释规范

### 7.1 注释语言与内容

- 业务代码、合同、测试和重要配置使用中文注释。
- 注释说明用途、业务含义、设计原因、数据来源和生效边界。
- 权限、数据源、SQL 编译、口径、记忆和审计相关逻辑必须说明关键业务规则及其依据。
- TypeScript 类型别名、接口和枚举都必须有用途注释；公共合同、领域类型与关键接口保留充分的业务说明。
- 对普通语法和名称已经清楚表达的信息保持简洁；特殊技术选择、非直观转换和容易误读的机制按需解释。
- 复杂校验前集中说明业务规则，再由代码表达具体判断分支。
- 注释中的授权、隔离、原子性等保证必须与实际实现一致，明确保证来源和适用范围。设计依据尚未确认时，准确描述已知事实。
- 代码行为变化时同步核对注释；测试注释中的用例承诺必须与实际输入、操作和断言范围一致。

### 7.2 JSDoc

以下说明使用 `/** ... */`：

- Schema、类型、接口、类和公共函数的用途与边界。
- 公共合同和领域对象字段的业务含义。
- 重要常量的含义、单位或约束依据。
- 非直观规则、算法和数据转换的原因。

函数内部的临时对象、局部步骤和测试准备根据阅读需要补充说明。测试场景背景和局部步骤说明可以使用 `//`。

```ts
/** API 已计算的一条行级授权范围类型。 */
type ResolvedRowScope = z.infer<typeof resolvedRowScopeSchema>;
```

## 8. 权限与 Data Access Service 规范

- API 保存角色对象权限、列权限和行策略，以及批准关系、数据集粒度、唯一键、关联基数和指标统计规则。
- API 在每次工具查询时依据当前身份重新校验权限，完成对象、字段、Join、参数、行条件、去重和聚合处理，再生成最终 DSL。
- `access` 至少包含用户、组织、分析运行、策略版本、过期时间和结果脱敏规则。
- 模型只调用 API 工具；API 每次调用 Data Access Service 时构建 `{ access, query, signature }`，并在受信任请求头携带短时 JWT。
- API 按 DSL 别名、对象范围和关联语义放置条件。主对象权限独立生效；需要保留主记录的外连接，可选侧限制采用对象预过滤或对应 `ON` 条件；查询级筛选放入 `query.filters`。`signature` 必须覆盖 `access` 与最终 `query`。
- 参数化数据集存在行限制时，API 通过受控参数强制绑定并校验授权范围；缺少可执行的权限参数时拒绝查询。固定输出同样执行列权限校验和输出脱敏规则计算。
- 关联可能导致业务记录重复时，API 按指标的去重键、聚合层次和总计规则生成查询。不同日期依据使用独立指标定义，执行记录保存固定时间依据及实际对象、字段和指标版本。
- Data Access Service 校验 JWT、整体签名、过期时间、本地数据源、对象白名单和可编译性。
- Data Access Service 只能执行 DSL 编译得到的参数化只读请求。
- Data Access Service 返回标准化结果、列信息、截断状态和可选新鲜度；审计关联信息写入 DAS 自身审计库。

### 8.1 分析、报告与运行规范

- Skill 描述通用分析方法、查询分支判断和结束条件，模型根据运行时指标定义、授权目录及证据决定实际分析路径。真实案例用于完善方法，确定性计算与权限控制由 API/工具执行。
- 报表模板按当前访问者权限执行；历史快照的查看、分享和导出同时校验报告访问权及其完整数据范围。权限不足或覆盖范围无法确认时拒绝原快照，可创建按访问者权限执行的新结果。
- API 持久化组织、用户、会话和运行归属，隔离 Agent 上下文，并对 SSE 订阅、回放和所有运行操作校验身份。
- 运行状态按合法状态转换原子更新；操作使用幂等键，澄清回答绑定待处理问题，状态与事件同事务提交。执行租约使用递增代次，过期执行器的提交被拒绝；取消后晚到结果不能覆盖终态。
- 第一版同一会话串行推进运行，不同会话可以并行。恢复依据持久化状态、问题、事件和执行检查点进行。
- 新增 DSL 或运行合同能力先完成共享 Schema、生成与执行支持及场景验收，再开放相应查询。设计文档中的待实现要求与代码完成状态分别维护。

## 9. 测试规范

所有应用和共享包采用 BDD 场景与 TDD 流程。先将需求写成明确的业务场景和验收预期，再编写对应的可执行测试，最后依据这些测试编写业务实现。场景和测试共同约束实现范围，确保代码沿既定业务目标推进。

新增功能或改变行为时，必须按以下编写顺序执行：

1. **编写 BDD 场景**：明确前提、操作或输入、预期结果，覆盖正常、异常和关键业务边界。
2. **编写 TDD 测试**：将已定义的场景落实为测试数据、操作和可执行断言，预期结果依据需求确定。
3. **确认预期失败**：运行新写的测试，确认失败来自目标行为尚未实现或既有缺陷；先处理环境、依赖或测试自身的问题。
4. **编写业务实现**：以已定义的场景和测试为验收依据，使测试通过，并完成相关回归。
5. **整理代码结构**：在行为测试保护下改进结构和表达，保持已确认的行为。

测试预期的调整必须有对应的需求依据。行为保持一致的结构重构先核对场景与已有测试，关键行为缺少覆盖时先补充场景和测试，再调整结构；已有测试的执行结果用于建立回归基线。

### 9.1 测试位置、场景与命名

```text
src/query/query-dsl.ts
tests/query/query-dsl.test.ts
```

- 默认包测试使用 `*.test.ts`，目录按业务分类镜像源代码目录。需要外部数据库的集成用例使用 `tests/integration/*.integration.ts`，由专用配置和命令收集；根目录工程工具的测试放在 `scripts/tests/*.test.mjs`。
- 使用中文 `describe` 和 `it` 描述业务范围、场景与预期行为；复杂场景可在相关实施计划中补充前提和验收说明。
- 每个用例围绕一个可独立判断的行为组织，失败信息应能定位对应场景。
- 额外注释用于补充业务背景、特殊测试准备、技术边界或容易误解的断言；注释是否需要由其信息价值决定。
- 业务背景与本用例验证范围分别表达，用例名称和注释应与实际断言匹配。

查询请求结构校验的场景示例：

| 前提与操作                               | 验收预期                                 |
| ---------------------------------------- | ---------------------------------------- |
| 提交结构合法且包含整体签名字段的查询请求 | 校验通过，查询内容和签名字段被正确读取。 |
| 提交缺少整体签名字段的查询请求           | 校验拒绝。                               |
| 提交携带未声明字段的查询请求             | 校验拒绝。                               |

先依据上述场景编写测试，再实现相应请求合同。测试说明可以集中交代本组用例的边界：

```ts
// 本组用例检查请求结构；签名真实性需要由验签流程验证。
it("请求结构合法且包含签名字段时通过", () => {
  const result = dataAccessQueryRequestSchema.parse({
    ...base,
    signature: "sig-v1-abc",
  });

  expect(result.query.source_id).toBe("clinical");
  expect(result.signature).toBe("sig-v1-abc");
});
```

其中 `base` 使用结构合法的测试请求，完整样例见 [查询请求合同测试](../ai-data/packages/contracts/tests/query/data-access-request.test.ts)。

### 9.2 合同测试要求

每个 Schema 至少覆盖：

- 合法输入。
- 缺失必填字段。
- 不合法枚举、格式、范围或日期。
- 未知字段被 `.strict()` 拒绝。
- `superRefine`、权限范围、资源上限等关键业务边界。

权限和查询相关合同还必须覆盖：

- 未授权对象。
- 未授权字段。
- 无效行范围。
- 查询上限。
- SQL 标识符注入片段。

端到端行为还必须覆盖：外连接可选侧无匹配行、主对象权限、多明细重复统计、参数化查询权限不可表达、固定时间口径、快照数据范围不足、重复澄清提交、取消后的晚到结果、租约接管后的旧执行器提交，以及跨用户事件订阅。

### 9.3 驱动替身与集成验证

- 替身遵守依赖接口的真实行为。数据库返回行数受生成 SQL 的 `TOP`、`LIMIT` 或 `FETCH` 限制，不能用超出该限制的模拟结果证明截断检测正确。
- 关系查询用 N+1 行探测是否超过返回上限 N，出口最多返回 N 行；固定存储过程按实际返回结果集判断并裁剪。两类路径分别覆盖空、少于、等于和超过上限的结果。
- 默认 `pnpm test` 包含工程规则和所有包级测试。各包声明测试命令时，应有对应职责的行为用例。
- 真实数据库集成验证通过独立入口运行，明确配置来源、环境要求、测试数据隔离和资源清理方式。缺少环境时记录未实跑状态，不能将替身验证或跳过用例记为集成通过。
- SQL Server 入口、配置示例和运行步骤见 [测试运行说明](../ai-data/TESTING.md)。

## 10. 文档规范

- 架构、合同、依赖和开发清单分别维护在 `需求文档` 目录。
- 代码行为改变时，同步更新对应设计文档和开发清单。
- 文档示例使用虚构 ID、测试数据或脱敏数据。
- 文档中的字段名、事件名、工具名和目录结构必须与当前代码合同一致。
- 每个新协议、新服务边界或重要决策都要有明确的职责、输入、输出和调用方说明。

## 11. 提交前验证

修改一个包后，在该包目录或根目录执行：

```powershell
pnpm --filter @ai-data/contracts format:check
pnpm --filter @ai-data/contracts typecheck
pnpm --filter @ai-data/contracts test
```

各应用和共享包完成后，根目录统一执行：

```powershell
pnpm format:check
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

验证失败时，先定位失败的合同、类型、格式或测试边界，再提交后续变更。

## 12. 新功能变更清单

新增功能时依次确认：

1. 所属应用或共享包是否正确，是否需要新增或修改跨服务合同。
2. BDD 场景是否写清前提、操作和验收预期，覆盖正常、异常与关键边界。
3. 对应 TDD 测试是否已编写，并确认因目标行为尚未实现而失败。
4. 实现、Schema、类型和业务注释是否满足已定义的场景与断言。
5. 公共 contracts 是否已从 `src/index.ts` 导出。
6. 权限、审计、数据新鲜度和只读边界是否明确。
7. 设计文档与开发清单是否同步。
8. 格式、类型检查、测试和构建是否通过。
