# AI BI 产品需求基线

版本：v0.2  
设计基线日期：2026-09-11  
状态：已确认的产品设计基线；新增能力待实现与验收

## 1. 产品定位

本产品是面向运营、业务和管理者的对话式 BI。用户可以用自然语言查询业务数据、连续追问、获得表格/图表/分析报告，并围绕异常变化完成原因归因。

产品目标不是一个“生成 SQL 的聊天框”，而是一个能够可靠理解业务口径、在受控数据范围内查询、给出有证据的结论，并逐步沉淀业务知识的 AI 分析师。

## 2. 已确认目标

- 自然语言查询业务指标、趋势、明细汇总和同比/环比。
- 支持多轮上下文追问，例如“排除华东再看”“按渠道拆开”。
- 支持解释指标定义，例如“销售额如何计算”。
- 支持自动输出表格、适当图表、结论、筛选条件和数据证据。
- 支持 Skill 引导的动态分析，围绕“为什么变化了”选择查询、验证假设并持续积累真实案例。
- 支持保存和分享有价值的分析报告。
- AI 必须在查询前确认业务口径；口径不清时请求澄清，不能静默猜测并返回错误数据。
- 同一指标在关联查询和维度汇总中保持其定义规定的粒度与总量，查询结果必须同时符合业务口径和当前用户权限。

## 3. 非目标（当前阶段）

- 不执行任何业务数据写入、删除或修改。
- 不做主动异常预警、定时推送或自动通知。
- 不做自动执行运营动作。
- 不优先做完整传统 BI 看板编辑器。
- 不优先做复杂预测、训练模型或自动化业务决策。

## 4. 总体架构边界

```text
用户 / Web 对话界面
        |
AI BI 后端
  |- Codex Harness：Agent 执行底座
  |- 业务知识与指标口径服务
  |- 记忆服务
  |- 报表、图表、证据链
        |
只读 Data Access Service（可插拔数据源连接器）
        |
数据库 / 数仓 / 外部只读 API
```

### 4.1 Codex Harness 的职责

Codex Harness 作为 AI Agent Runtime，负责：

- 多轮对话与上下文任务执行。
- 调用 API 提供的目录和查询工具。
- 任务拆解、查询编排、重试与结果解释。
- 当信息不完整时发起澄清。
- 依据 Skill、运行时指标知识、当前目录和已取得证据选择分析查询与后续分支。
- 流式输出进度和最终结果。
- 生成分析摘要和报告。

Codex Harness 不是整个产品。业务知识、记忆、权限、审计、UI 和数据访问边界由产品自身掌控。

业务 API 管理指标定义、已批准关系、关联键和基数、指标粒度、去重、聚合及上卷规则，并据此完成全部业务查询构造。API 工具承担确定性计算、权限校验、运行状态和证据持久化；Agent 在这些受控能力内动态推进分析。

### 4.2 Data Access Service 的职责

- 提供唯一的数据访问入口。
- 向 API 返回当前可用的数据源纯目录：表/资源、字段、类型、注释和基础查询能力；Catalog 不包含原始样例、敏感分类或脱敏策略。
- 严格校验 API 提交的内部请求 `{ access, query, signature }`，将逻辑对象映射到本地白名单，编译并执行业务语义和授权范围均已由 API 确定的只读 DSL，再按 API 签名规则执行输出脱敏或匿名化并返回结构化结果。
- 通过可插拔连接器适配 SQL Server、HTTP API 等数据源；不向 Agent 暴露数据库方言、连接串或接口密钥。
- HTTP API 连接器只在 DAS 内部使用 Axios 处理超时、拦截和响应预处理，再按已配置的 JSONPath 提取、类型转换和扁平化，向 API 返回统一表结构；不返回原始 JSON、JSONPath、接口地址或接口密钥。
- 数据源账号或 API 凭据仅由 Data Access Service 的受保护运行配置使用；Codex Harness 不接触凭据。
- 服务通过唯一的 `das.config.json` 加载 API Host、JWT 验签公钥和 DAS 元数据 SQL Server 连接；数据源连接配置、允许向 API 暴露的对象配置和审计数据持久化在 DAS 自己的 SQL Server 中。每个 API 查询请求本身不保存会话状态。
- SQL Server 连接器仅允许 `SELECT`；其他只读连接器只能调用其查询能力，并统一限制超时、结果量、速率和成本。
- 将查询执行、拒绝、超时和失败事件写入 DAS 自身的审计库，并向 API 返回可关联的审计信息。
- 按固定间隔向 API 发送服务心跳，并在心跳中报告各 `source_id` 的健康状态；API 根据最近心跳和失联阈值决定是否继续调度查询。
- 不负责指标识别、业务口径、记忆、Skill、学习或原因归因，也不保存 API 的用户、角色或原始权限策略。

API 与 Data Access Service 的内部查询请求固定为 `{ access, query, signature }`，并通过短时 JWT 识别调用方。API 按关联语义确定用户条件与权限条件的准确作用位置，最终 DSL 完整表达这些决策，`signature` 覆盖 `access` 与 `query`。签名算法、重放防护、密钥托管和传输认证在 Data Access Service 部署安全设计阶段确定。

### 4.3 查询正确性与数据权限

- 主对象的行权限始终生效。外连接的可选侧没有获授权的匹配数据时，应保留该查询语义要求保留的主侧记录，可选侧呈现空值；用户明确要求“存在匹配”时，由 API 按该意图构造查询。
- API 按已批准关系及指标规则构造关联、去重和聚合，避免一对多或多对多关联重复计算指标。维度拆分和上卷必须保持指标定义要求的总量；不能直接求和的指标按其定义重新计算。
- 存储过程和 HTTP 参数化数据集存在行范围限制时，API 必须通过受控参数落实限制，并覆盖或校验用户输入。限制无法表达或无法确保执行时，拒绝该查询。
- 固定结构的参数化结果仍须进行列授权与脱敏校验，获准调用数据集不代表可读取其全部输出列。
- DSL 或连接器尚不能准确表达所需过滤位置、粒度或聚合语义的查询，须先补齐合同和执行能力并验收后开放。

## 5. 主对话流程

```text
用户问题
-> 识别指标、时间、范围、维度、比较基线
-> 读取已发布口径、会话确认和用户偏好
-> 需要解析执行对象或口径信息不足：通过 API Catalog 工具探索候选对象
-> 影响结论的口径不明确：展示结构化选项，等待用户确认
-> 形成或确认本次查询意图
-> API 将受控查询请求交给 Data Access Service
-> 动态执行分析步骤并记录假设、查询和证据
-> 输出结论、表格/图表和证据
-> 接收后续追问，沿用已确认上下文
```

每个数据结果应包含或可展开查看：

- 指标定义及版本。
- 时间范围、筛选条件、对比基线。
- 数据来源或查询证据。
- 数据更新时间。
- 已验证结论与待验证假设的清晰区分。

数据探索不能因一次关键词检索未命中而停止。Agent 根据已知信息选择业务词扩展、当前授权目录、候选对象详情与有限数据画像；只有在仍无法确认数据对象或指标口径时，才说明缺失信息并请求用户帮助。目录探索用于落实已选指标的定义。每次查询以当前目录和执行时校验结果为准，并保留指标版本、实际对象、字段和关联关系，确保结果可追溯。

数据库注释、接口描述和字段元数据可以作为发现依据，但不是所有数据对象都必须预先补齐业务说明；缺失或冲突的说明应进入候选确认流程。字段敏感性、字段可执行操作、Join 和行权限由 API 的权限策略计算并校验后写入 DSL；需要返回脱敏的列由 API 放入已签名的 `access.output_masks`，Data Access Service 只执行该规则，不根据字段名自行推断。

## 6. 口径澄清与人机交互

当指标、时间、范围或维度存在歧义时，模型通过 SSE 返回问题和选项，前端按统一事件格式渲染并提交用户选择。问题和选项由模型按当前业务上下文生成，不预设为字段配置。

示例：

```json
{
  "type": "clarification",
  "question": "“销售额”指哪个指标？",
  "options": [
    { "id": "paid_gmv", "label": "支付 GMV" },
    { "id": "net_sales", "label": "净销售额" },
    { "id": "order_amount", "label": "下单金额" }
  ],
  "allow_custom_input": true
}
```

以上为交互内容示意；实际事件还须携带会话、运行和澄清标识。前端回传对应标识及所选选项 ID 或自定义输入，API 校验归属和待答状态后恢复同一分析任务。刷新、重复提交和重连不能造成重复执行或将答案提交到另一任务。

## 7. Skill 引导的动态分析

围绕“为什么下降/上涨”，Skill 提供可复用的调查方法，例如确认比较基线、核对变化、选择拆解维度、量化贡献、验证候选解释和整理证据。模型结合运行时的指标定义、授权目录和查询结果，决定本轮查询及后续分支。一次分析可能经历：

```text
确认异常和比较基线
-> 选择可能的拆解维度
-> 按维度量化变化与贡献
-> 继续下钻和验证假设
-> 输出数据支持的结论、证据、影响范围与未证实假设
```

该过程允许循环、跳过不适用的步骤、请求澄清或结束分析。Skill 可以包含真实案例示例；具体方法通过真实业务分析持续完善。首个 Skill 和端到端闭环以通用调查方法、可用工具及证据记录为基础，运行时再形成适合当前指标的分析路径。

API 工具执行确定性计算、权限校验并保存当前步骤、假设、下一步目标、查询结果摘要和证据关系。每次运行持久化查询次数、步骤数、耗时和成本等限制；达到限制时，返回已有证据、尚未解决的问题和停止原因。

分析结果应区分：

- 已由数据验证的驱动因素。
- 合理但尚未验证的假设。
- 因数据缺失、口径限制或权限限制而无法判断的部分。

结论强度必须与证据匹配。变化贡献、相关性和因果解释需要分别表述；贡献排序本身只能支持变化分布判断。业务知识缺失时，先探索或澄清，并保留不确定性。

## 8. Skills、业务知识与记忆

四类资产必须分开管理：

| 类型         | 作用              | 示例                                 |
| ------------ | ----------------- | ------------------------------------ |
| Skills       | AI 如何工作       | 通用调查方法、动态分析指引、报告方法 |
| 企业业务知识 | AI 信任的正式事实 | 指标公式、维度定义、业务规则         |
| 用户记忆     | 某用户的稳定偏好  | 默认区域、常用口径、展示偏好         |
| 分析案例     | 可复用的分析方法  | 异常拆解路径、查询证据               |

向量检索不是基础设施前提。初期优先级：

- Skills 用 Git 管理的 Markdown/目录表达分析方法，运行时读取当前可用内容。
- 指标定义用结构化、可版本化数据表达。
- 用户偏好用结构化数据库记录。
- 文档规模变大或需要案例相似检索后，再引入向量检索。

### 8.1 指标定义

指标定义是数据合同，至少需要：

- 指标 ID、名称和别名。
- 公式与说明。
- 固定的时间归属、指标粒度、去重键、聚合和上卷规则。
- 可使用的数据源能力和业务范围；具体对象在当前目录中动态发现。
- 允许的维度和筛选条件。
- 生效时间、版本、负责人和发布状态。

正式指标定义用结构化数据保存业务规则；执行对象依据统一表目录、参数化查询定义和 API 已批准关系动态解析。

不同时间归属对应不同指标 ID 和定义，例如“门诊人次（挂号时间）”与“门诊人次（就诊时间）”分别固定使用挂号时间和就诊时间。选择指标即选择其时间口径；用户改变时间归属时，系统明确选择另一个指标。目录发现只解析当前指标所需对象和字段，运行记录保存所用指标版本及实际解析结果。

### 8.2 记忆优先级

```text
已发布企业口径
> 当前会话已确认选择
> 当前用户个人默认
> 历史分析案例
> 模型推断
```

### 8.3 记忆写入规则

- 当前任务和已确认条件：写入会话记忆。
- 用户明确确认的个人偏好：立即写入个人长期记忆。
- 用户提出的新业务规则：写入企业知识候选，不直接发布。
- 高质量的完整分析：可保存为分析案例，记录方法、口径、条件和证据；旧数值不作为当前事实复用。
- 普通查数、临时筛选、猜测、闲聊和未完成分析：不进入长期记忆。

## 9. 受控学习与确认机制

系统学习是受控的知识沉淀，不是模型自行修改全局知识：

```text
对话 / 用户纠正 / 完成报告
-> 识别候选
-> 去重、分类、提取证据
-> 用户确认或负责人审核
-> 发布到对应记忆层
```

- 个人确认的口径可立即成为该用户的默认口径。
- 同一候选获得其他用户认可时，仅增加支持证据和置信度。
- 企业级口径必须由有权限的指标负责人审核、设定范围和版本后发布。
- 新用户没有个人默认、且企业未发布统一口径时，AI 必须继续澄清，不得把候选当作事实。

## 10. 分析运行与后台可靠性

### 10.1 前台分析运行

- 每次分析持久化独立运行状态，按组织、用户、会话和运行隔离；Agent 上下文、查询结果和证据遵循相同边界。
- SSE 订阅、断线补发、澄清提交、取消、恢复和结果读取均验证当前访问权限。
- 第一版同一会话的活跃运行串行执行；等待澄清的运行仍占用该会话的活跃位置。不同会话可在资源上限内并发执行。
- 创建运行、提交澄清和记录工具结果具备幂等性，状态变更须原子提交。
- 执行租约标识当前有效执行者。租约过期后恢复执行时，旧执行者的迟到写入不得覆盖当前状态。
- 用户可取消运行；取消之后的迟到查询或模型结果不得进入正式回答、证据或报告。
- 服务重启后可从持久化状态恢复可继续的任务，并保留已完成步骤、待答澄清、剩余运行额度和审计记录。

### 10.2 后台记忆任务

对话完成后，可以选择性创建记忆事件。并非每轮都调用后台 Agent；普通查数通常不需要处理。

初期可以使用数据库任务表，不需要先部署复杂队列或多个 Worker：

```text
对话回答完成
-> 写入 memory_event（pending）
-> 后台低优先级、限并发领取任务
-> no_op / 创建候选 / 发起确认
```

可靠性要求：

- 前台对话不等待学习任务完成。
- 任务有 `pending`、`processing`、`done`、`failed` 等状态。
- 使用租约/锁防止多实例重复领取同一任务。
- 处理具备幂等性、失败重试和超时回收。
- 后台任务有独立并发上限，不能挤占前台请求、数据库连接或模型调用配额。

初期可在同一后端进程中运行前台服务和低优先级任务循环；负载增加后，再把相同任务逻辑迁移到独立 Worker 或消息队列，无需改变业务模型。

## 11. MVP 范围

按真实业务价值逐步交付：

1. 选择一个真实指标和两个具有不同数据范围的角色，完成口径澄清、授权查询、多轮追问及证据展示。以现有认证、组织角色、会话、运行记录、目录和 DAS 心跳基础承载闭环，并补齐查询正确性、运行隔离和恢复能力。
2. 基于该指标的真实案例迭代动态分析 Skill，验证模型依据结果选择分支、确定性计算可复核、结论可回溯，并逐步沉淀用户偏好、知识候选和分析案例。
3. 在闭环稳定后扩展指标与角色，丰富报告、画布、分享和导出体验。

以上为交付顺序与验收目标。既有基础设施和已完成事项以开发清单记录为准，新增设计须经实现和验证后验收。

## 12. 报告、模板与快照权限

- 报告模板保存可重用的分析意图和呈现结构，每次运行使用查看者当前权限，并生成属于该次运行的新结果与证据。
- 历史快照固定保存当时的内容、指标版本、条件、数据范围及证据。查看者须同时通过报告 ACL 和完整底层数据范围校验。
- 校验覆盖快照中的表格、图表、文字结论及导出内容；所有内容依赖的数据对象、行范围、字段和敏感数据处理要求均须满足当前权限。
- 权限不足时拒绝读取或导出该快照。查看者可在自身授权范围内发起新执行，生成新的结果；原快照保留。
- 分享与导出遵循相同授权规则，不能通过摘要、图表或静态文件绕过数据范围控制。
