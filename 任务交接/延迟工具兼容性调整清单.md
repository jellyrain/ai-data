# 延迟工具兼容性调整清单

日期：2026-09-27。状态：用户已批准，实施与验收完成。本清单仅调整已批准任务中的第 3 项，结果见[交付说明](上下文按需加载与自动压缩交付说明.md)。

## 发现的问题

当前 Codex 0.154.0 接口虽然接受 `deferLoading` 字段，但扁平工具设置该字段会被拒绝，错误为 `deferred dynamic tool must include a namespace`。隔离线程改成官方命名空间形式后，实际发送给当前自定义提供方的请求没有该业务工具，也没有 `tool_search`；rj 返回 completed，业务工具调用次数为 0。因此单独开启该标识不能完成按需加载。

同版本官方源码中，工具发现要求模型元数据支持搜索且提供方支持命名空间；当前接入未满足该路径。[工具发现启用条件](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/spec_plan.rs#L599)。实际证据见[隔离线程请求](上下文按需加载与自动压缩验收/延迟工具兼容性.json)。另一次直接发送 `tool_search` 类型的短请求返回 200、仅包含 reasoning 项；这不能证明发现协议已经可用，也不能单凭这一结果认定模型服务全面不支持该类型。

## 建议的替代范围

继续使用已能运行的普通函数调用，新增参数定义读取函数。大型工具完整参数按需读取，业务函数名称、服务实现及授权校验继续复用。

1. 新增普通函数 `get_tool_schema`，输入为工具名，只返回当前 Agent 已允许工具的完整参数定义；不可用的工具名称和结构不对模型暴露。
2. `query_dataset`、`save_report_definition`、`save_user_preference`、`create_knowledge_candidate` 四个大型工具在新 Agent 中提供简短入口，参数为 `arguments_json` 字符串。
3. 模型先读取需要的参数定义，再把原业务参数对象序列化后提交给对应原名工具。API 限制字符串大小、解析 JSON，再走原完整 Zod 校验、授权、租约、幂等、证据及审计路径。
4. 小型查询、目录、详情、指标执行等工具继续使用现有明确参数；读取过的定义可随官方线程复用，压缩后需要时重新读取。
5. 在新发布的专用验收 Agent 和默认 Agent 后续版本中明确启用 `get_tool_schema`；旧 Agent 沿用原参数入口。接口授权集合变化遵循现有线程兼容性规则。
6. 真实 rj 验证“读取定义 → 参数化调用 → 正确结果”，并覆盖错误 JSON、越权读取、无效业务参数、压缩后重读和恢复。

代价：首次使用某个大型工具增加一次定义读取；模型需要正确生成 JSON 字符串，错误率和额外调用耗时纳入验收。该方式使用普通函数，不依赖官方的专用工具发现请求类型。
