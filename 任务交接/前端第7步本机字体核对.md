# 前端第 7 步本机字体核对

日期：2026-09-28。用户提出优先使用本机字体。本次完成只读核对，资源与 PDF 字体映射尚未替换。

## 使用方式

网页以及 Word／Excel 可以按字体族名称使用阅读机器上已有的字体。当前选用的 pdfmake 生成可搜索文字时，需要实际字体数据；仅指定一个系统字体名称不能完成 PDF 嵌入。[pdfmake 官方字体文档](https://pdfmake.github.io/docs/0.3/fonts/custom-fonts-client-side/url/)。

如果每次导出直接读取访问者的操作系统字体，需要 Local Font Access API 的用户授权，且浏览器支持有限。该方式会增加导出交互和环境要求。[MDN 本地字体接口](https://developer.mozilla.org/en-US/docs/Web/API/Window/queryLocalFonts)。

建议优先复用开发机现有的 Noto Sans SC，核对许可并通过兼容验证后作为项目静态资源，PDF 导出按需读取并嵌入。字体随 Web 部署，生成后的 PDF 自带所需字形。Noto Sans SC 的上游采用 OFL-1.1，分发时保留版权及许可。[上游许可证](https://raw.githubusercontent.com/google/fonts/main/ofl/notosanssc/OFL.txt)。

## 库的默认字体核对

用户追问默认字体后，直接检查已安装的 pdfmake 0.3.11：`build/vfs_fonts.js` 自带 Roboto 的常规、中等、斜体和中等斜体四份字体。用其实际依赖 fontkit 逐个检查“住、院、费、用”四个字符，四份字体均无对应字形。因此此前英文 PDF 验收能够通过，中文 PDF 仍需提供包含中文字形的字体资源。[默认字体官方说明](https://pdfmake.github.io/docs/0.3/getting-started/client-side/)。

ExcelJS 和 docx 生成的文件可以保存中文文字及字体名称，由 Excel／Word／兼容软件使用阅读机器上的字体排版；当前方案无需给这两类文件额外嵌入字体。补充中文字体的直接需求来自 pdfmake 中文 PDF，分享功能也不依赖这项资源。字体作为项目资源准备即可，最终用户无需另外在操作系统安装。

## 微软雅黑资源请求与许可核对

用户随后要求“挪微软雅黑”。按字体复用的任务意图，预期操作为复制到项目，保留 Windows 系统原文件。本机存在 `C:/Windows/Fonts/msyh.ttc`（19,704,352 字节）和 `msyhbd.ttc`（16,883,552 字节）。

微软的[字体许可 FAQ](https://learn.microsoft.com/en-us/typography/fonts/font-faq) 明确区分以下用途：CSS 可以引用系统字体名称；符合字体嵌入标志等条件的文档嵌入可能获准；Windows 附带许可不授予将字体复制到 Web 服务器、随应用分发的权利。[微软雅黑官方页面](https://learn.microsoft.com/en-us/typography/font-list/microsoft-yahei) 同时列出针对 Web／软件分发的额外授权入口。

当前方案需要把字体放入 Web 静态资源并供浏览器获取，属于需要另外确认授权的使用方式，不能仅依据系统已安装字体判断可随项目分发。结合用户之前要求全部免费，已提出两个明确选择：复用本机已有的 OFL 字体 Noto Sans SC；或在用户确认已有覆盖 Web 分发的微软雅黑授权后，按其许可范围继续。

本轮完成路径、文件大小及官方许可的只读核对，未复制微软雅黑、未删除系统文件、未更改 PDF 字体映射。等待该字体来源选择；依赖新增与安装操作为 0。
